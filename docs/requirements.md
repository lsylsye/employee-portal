## 1. 성명 → firstName / lastName 변환 (시드 데이터 분석)

외부 API는 `firstName`/`lastName`을 요구하는데, 사내 데이터는 한글 성명 하나뿐이다.
**문자열 규칙으로 자동 분리하면 틀리는 경우가 있다.** 그래서 성과 이름을 별도 컬럼으로 저장하고, 시드에서 명시적으로 분리하는 것을 전제로 한다.

| 사번 | 성명 | 성 / 이름 | 문제 유형 | 비고 |
|---|---|---|---|---|
| EMP-001 | 김민준 | 김 / 민준 | **동명이인** | EMP-002와 성명이 같다. 사번·생년월일로 구분한다. UI에서는 성명만 보여주지 않는다. |
| EMP-002 | 김민준 | 김 / 민준 | **동명이인** | 〃 |
| EMP-003 | 남궁서준 | 남궁 / 서준 | **복성** | 앞 1글자로 자르면 `남 / 궁서준`이 되어 틀린다. |
| EMP-004 | 황보라온 | 황보 / 라온 ⚠️ | **복성 여부가 애매함** | `황 / 보라온`도 가능한 이름이다. 문자열만으로는 판별할 수 없다. |
| EMP-005 | 김솔 | 김 / 솔 | **외자** | 이름이 1글자다. 외부 API가 받아주는지 🔬 확인한다. |
| EMP-006 | 선우진 | 선우 / 진 ⚠️ | **복성 여부가 애매함 + 외자** | `선 / 우진`도 가능하다. 복성이면 이름이 외자가 된다. |
| EMP-007 | 이서연 | 이 / 서연 | **생년월일 미확인** | API가 `dateOfBirth`를 필수로 요구하므로 **BG 조회를 실행할 수 없다.** 임의 날짜로 채우지 않는다. |
| EMP-008 | 박민준 | 박 / 민준 | — | 이름 `민준`이 001, 002와 같다. 이름만으로 검색하면 섞인다. |
| EMP-009 | 최지우 | 최 / 지우 | — | |
| EMP-010 | 정하윤 | 정 / 하윤 | — | |

추가로 판단할 것:
- ⚠️ **lastName = 성**이다. 영어의 "last"는 순서가 아니라 family name을 뜻한다. 한국 이름 순서(성이 먼저)와 헷갈리지 않게 매핑 코드에 명시한다.
- ⚠️🔬 **한글로 보낼지, 로마자로 보낼지.** 명세 예시는 영문(`John`/`Doe`)뿐이고 문자셋 규정이 없다.
  - 로마자 변환은 한 이름에 여러 표기가 나온다(김 → Kim/Gim, 이 → Lee/Yi/Rhee). 여권 영문명 같은 공식 표기가 사내 데이터에 없어서 변환하면 오히려 부정확해진다.
  - 먼저 한글이 받아지고 응답에도 그대로 돌아오는지 실측한다.
- ⚠️ 애매한 두 건(황보라온, 선우진)은 **복성으로 판단**하고 DECISIONS.md에 근거를 남긴다. 관리자가 성·이름을 수정할 수 있게 한다.
  - 복성으로 본 근거: 과제가 "흔히 나타나는 형태"를 일부러 넣었다고 밝혔다. 목록에 남궁도 함께 있다.
- 시드 목록은 수정하거나 빼지 않는다. 원래 성명 문자열은 보존하고, 성·이름 컬럼을 **추가로** 둔다.

### 놓치기 쉬운 것 / 판단이 필요한 것 ⚠️

|---|---|---|
| F-a | **"인적사항"에 어떤 필드를 넣을지** | 시드에는 사번·성명·생년월일뿐이다. 수정할 거리가 있으려면 연락처, 이메일, 주소, 비상연락처 같은 필드를 정해야 한다. |
| F-b | **직원이 수정할 수 있는 필드와 없는 필드** | 성명·생년월일은 BG 조회의 입력값이다. 직원이 마음대로 바꾸면 조회 결과와 신원이 어긋난다. HR 관리 필드와 본인 수정 필드를 나누는 게 자연스럽다. → 판단 (4) |
| F-c | **관리자 계정을 누구로 할지** | 관리자는 시드 목록에 없다. 목록을 수정하지 말라는 조건이 있으므로 직원 레코드가 없는 별도 계정으로 둘지, 시드 직원 중 한 명에게 권한을 줄지 정해야 한다. |
| F-d | **로그인 아이디와 초기 비밀번호 방식** | 사번을 아이디로 쓸지, 계정 생성 시 초기 비밀번호를 어떻게 전달할지, 첫 로그인 때 변경을 강제할지 |
| F-e | **생년월일이 없는 직원(EMP-007)의 BG 처리** | 실행 버튼을 막고 "생년월일 확인 필요"를 표시한다. 관리자가 생년월일을 입력하면 실행할 수 있게 한다. |
| F-f | **BG 결과 이력과 재조회** | 같은 직원에게 여러 번 실행할 수 있는지, 이전 결과를 보여줄지. 외부 API 목록 조회로 이력을 가져올 수 있다. → 판단 (2) |
| F-g | **pending 상태의 UI** | 결과가 늦게 나오므로 "진행 중"을 표시하고 갱신 방식을 정한다(화면 폴링 / 서버 폴링). |
| F-h | **퇴사자 데이터** | 퇴사 후에도 목록에 남길지(상태 표시), 퇴사일을 예약할 수 있는지 → 판단 (1) |
| F-i | **동명이인이 구분되는 목록·검색 UI** | 목록에 성명만 있으면 EMP-001과 002를 구분할 수 없다. 사번과 생년월일을 함께 보여준다. |

## 3. 비기능 요구사항

### 보안
| ID | 내용 |
|---|---|
| N1 | 비밀번호는 해시(BCrypt)로 저장한다. 평문 저장이나 로그 출력은 금지한다. |
| N2 | **CSRF**: 세션 쿠키 인증이면 상태를 바꾸는 요청(POST/PUT/DELETE)에 CSRF 방어가 필요하다. SPA에서는 쿠키 토큰 방식을 쓴다. |
| N3 | **IDOR 방지**: 직원 API는 `/api/me`처럼 세션에서 본인을 식별한다. `/api/employees/{id}`에 id만 바꿔 넣어 다른 사람 정보를 보는 구조를 피한다. |
| N4 | **BG 결과는 민감정보**(`criminalRecord`, `creditScore`)다. 관리자만 열람하고, 직원 본인에게도 노출할지는 판단한다. 열람 기록을 남길지, 보관 기간은 얼마로 할지 → 판단 (3) |
| N5 | **최소 수집**: 외부 응답을 전부 저장할 필요는 없다. 필요한 필드만 저장하는 방안을 검토한다(예: `creditScore`는 채용 판단에 필요한가?). |
| N6 | 로그에 개인정보와 BG 결과를 남기지 않는다. API 호출 로그에는 checkId, 상태코드, 지연시간만 남긴다. |
| N7 | 후보자 키는 환경변수로만 다룬다(`BGCHECK_API_KEY`). 코드, 레포, 로그, **대화 원문 커밋**에 넣지 않는다. |

### 외부 API 연동의 신뢰성 (실측으로 값을 정한다)
| ID | 내용 |
|---|---|
| N8 | 타임아웃: 🔬 GET 지연 분포(p99, 최댓값)를 근거로 정한다. |
| N9 | 재시도: 🔬 500/503 비율과 `Retry-After`를 근거로 정한다. **POST는 멱등성이 확인되기 전까지 재시도하면 안 될 수 있다.** 5xx가 났는데 실제로는 생성됐다면 재시도가 중복 요청이 된다. |
| N10 | 폴링: 🔬 pending이 최종 상태가 될 때까지의 실제 시간과 `estimatedCompletionSeconds`를 비교해 주기와 최대 대기 시간을 정한다. |
| N11 | 중단 조건: 4xx(400/401/404)는 재시도하지 않는다. 최대 횟수나 최대 대기 시간을 넘으면 "확인 필요" 상태로 남긴다. |
| N12 | 외부 API가 실패해도 우리 앱의 다른 기능(로그인, 직원 관리)은 동작해야 한다. 장애를 격리한다. |

### 운영 / 기타
| ID | 내용 |
|---|---|
| N13 | 배포를 유지한다(평가 기간 동안 Railway 상시 실행). |
| N14 | 스키마를 재현할 수 있어야 한다(Flyway, 시드 포함). |
| N15 | 시간 표시: API는 UTC, 화면은 KST로 보여준다. |
| N16 | 6시간 예산: 범위를 줄이면 뺀 것과 이유를 문서화한다. |
| N17 | **실측 데이터로 앱 데이터를 오염시키지 않는다.** 실측 POST에 시드 사번(`EMP-001` 등)을 쓰면, 같은 키로 보는 앱과 평가자 화면의 BG 이력에 실측 요청 수백 건이 섞인다. 실측용 employeeId는 따로 쓴다(예: `MEAS-...`). |

## 4. 명세(swagger.yaml) 문제와 확인할 점

### 명세 자체의 결함 (문서에서 확인)
| # | 내용 |
|---|---|
| S1 | `components.responses.Unauthorized`가 없는 스키마 `#/components/schemas/Error`를 참조한다(`ErrorResponse`여야 할 것으로 보인다). |
| S2 | 401 응답이 정의만 되어 있고 **어느 경로에도 연결되어 있지 않다.** 설명에는 모든 요청에 키가 필요하다고 되어 있다. |
| S3 | **POST에는 201과 400만 있다.** 500/503이 명세에 없다. GET에는 둘 다 있다. 🔬 POST도 5xx를 내는지 확인한다. |
| S4 | 삭제 API가 없다. **외부에 저장된 BG 기록은 우리가 지울 수 없다.** 보관 기간 정책은 우리 DB에 대해서만 적용할 수 있다. → 판단 (3)에 영향 |
| S5 | 중복 요청과 멱등성에 대한 언급이 없다(멱등키 헤더도 없다). 🔬 |
| S6 | 요청 빈도 제한이 명시되어 있지 않다. 503 "overloaded"가 부하 때문인지 무작위인지 🔬 |
| S7 | `flagged`의 사유가 없다. 어떤 항목 때문에 flagged인지는 결과 필드(`criminalRecord` 등)로 추정해야 한다. |
| S8 | `firstName`/`lastName`의 문자셋·길이 규정이 없다. `dateOfBirth`가 없을 때 어떻게 되는지(400?)도 🔬 |
| S9 | 목록 API에 페이지네이션이 없고, 항목에 결과 상세가 없다. 결과를 보려면 건마다 GET해야 한다. |

### 실제 호출에서 이미 관찰한 것 (표본 약 6회, 정식 실측 전)
| # | 내용 |
|---|---|
| O1 | **형식만 맞으면 임의의 키도 200**을 준다(1회 관찰, 빈 목록). 명세의 "유효하지 않은 키는 401"과 다르다. 키를 잘못 넣으면 오류 없이 다른 공간에 데이터가 쌓인다. ⚠️ 이 관찰은 AI가 임의 키로 호출해서 얻은 것이다. **다른 지원자 키와 겹치면 남의 데이터를 읽게 되므로, 이후 본인 키 외의 호출은 하지 않는다**(사용자 지시). 재현 실험도 하지 않는다. |
| O2 | 목록 GET에서도 503(`retryAfter: 30`)과 500이 나왔다. 오류 빈도가 무시할 수준이 아닐 수 있다. |
| O3 | CORS 허용 헤더가 없다. 브라우저에서 직접 호출할 수 없으므로 **반드시 백엔드가 중계**해야 한다. 키를 브라우저에 노출하지 않는다는 점에서는 오히려 맞는 구조다. |

### 실측에서 확인할 것 (과제 요구 + 위에서 추가된 것)
- 과제 요구:
  - GET 상세 지연(p50/p95/p99/최댓값)
  - 상태코드 분포
  - 같은 employeeId로 POST를 반복할 때의 동작
  - pending에서 최종 상태까지 걸리는 시간
  - 동시 요청을 늘릴 때의 변화
  - 명세 대조
- 추가:
  - POST 5xx의 존재와 **5xx 뒤에도 실제로 생성됐는지**(목록으로 확인)
  - `Retry-After`가 헤더로 오는지, 본문으로만 오는지
  - POST가 즉시 `clear`/`flagged`를 주는 비율
  - `estimatedCompletionSeconds`의 정확도
  - 같은 사람을 반복 조회할 때 결과가 같은지(결정적인지)
  - 한글 이름, 외자, 생년월일 누락, 잘못된 날짜 형식에 대한 응답
  - 존재하지 않는 checkId를 **본인 키로** 조회할 때의 응답(404 형식). 다른 키의 데이터 격리는 명세 설명으로만 인용하고 직접 검증하지 않는다.
- **실측 원칙: 모든 호출은 본인 키(`BGCHECK_API_KEY`)로만 한다.** 임의 키, 다른 지원자 키, 키를 추측하는 호출은 하지 않는다.

## 5. 테스트 범위 — 꼭 필요한 3개만 (사용자 결정, 시간 제약)

시간이 부족해서 **실패했을 때 피해가 가장 큰 3개만** 자동 테스트로 둔다. 나머지는 수동 확인과 배포 검증으로 대신하고, 뺀 이유는 제출 문서에 적는다.

| # | 테스트 | 검증 내용 | 구현 브랜치 | 설계 제약 |
|---|---|---|---|---|
| T1 | **접근 통제** | 직원 계정으로 ① 다른 직원의 정보 조회·수정 ② 관리자 API(계정 생성, 목록, 퇴사 처리, BG)를 호출하면 **거부**된다(403). 로그인하지 않았으면 401. | `feat/auth` → `feat/admin-employee`, `feat/my-profile`에서 케이스 추가 | 직원 API는 `/api/me`처럼 세션에서 본인을 식별한다(N3). |
| T2 | **퇴사자 차단 (한국 시간 경계 포함)** | 퇴사 시점 **직전(KST)**에는 접근되고 **직후**에는 차단된다. 이미 로그인한 세션도 다음 요청에서 차단된다. 경계 예: KST 자정 = UTC 15:00 | `feat/auth`, `feat/admin-employee` | Railway 서버 시간대는 UTC다. 그래서 **현재 시각은 `Clock` 빈(Asia/Seoul)으로 주입**하고, 코드에서 시간대 없는 `LocalDate.now()`를 쓰지 않는다. 테스트는 고정 `Clock`으로 경계 직전과 직후를 만든다. 경계를 정확히 어디에 둘지는 DECISIONS (1)에서 정한다. |
